## FTW-23, COLMAP with CUDA (In Review)

- **colmap 3.13.0**, conda-forge build `cuda_126h5ca8012_3`, into the existing `recon` env. Not
  apt: jammy's package has no CUDA, and a source build wants a newer CMake than jammy ships.
- Deliberately 3.x. conda-forge also ships 4.x now, which is outside the pinned range and would
  change the CLI `ns-process-data` drives.
- Checked with `mamba install --dry-run` before committing to the shared env: install-only, 160
  packages, 392 MB, no upgrades/downgrades/removals, python and numpy untouched. So no need for
  the separate-env fallback. torch re-verified against the GPU afterwards, unaffected. Env is now
  6.8 GB.
- Done-when met: `colmap -h` reports **"(Commit Unknown on Unknown with CUDA)"**, and the binary
  links `libcudart.so.12`.
- Verified past the done-when, since "reports CUDA" is not "GPU SIFT runs": generated three
  synthetic 800x600 textured views with a stdlib PNG writer and ran `feature_extractor` with
  `use_gpu 1`. Extracted **2854 / 2856 / 2848** SIFT keypoints, written to the database, 2.4 s
  total.
- Worth knowing: the CUDA build matters more in WSL than it appears. COLMAP's non-CUDA GPU SIFT
  path goes through OpenGL and wants a display, which a headless WSL box has not got.
- `ceres-solver` is the CPU build, so bundle adjustment is CPU while extraction and matching are
  GPU. Fine at room scale.
- conda pulled `cuda-version 12.9` / `cuda-cudart 12.9.79` alongside torch's pip cu126 runtime.
  They coexist; torch resolves its own bundled libraries. Recorded in STACK.md as "do not align
  by hand".

## FTW-24, Nerfstudio with compiled CUDA extensions (In Review)

- **nerfstudio 1.1.5** from PyPI (the pin says current stable), **gsplat 1.4.0**. Done-when met:
  `ns-train --help` runs in 16 s and registers `splatfacto`, `splatfacto-big`, `splatfacto-w`.
- `tiny-cuda-nn` deliberately skipped: splatfacto uses gsplat, tcnn only accelerates nerfacto's
  hash encoding, so it is a long compile for a model we do not ship.
- **The ticket's warning was justified.** `gsplat-1.4.0` is a `py3-none-any` wheel with no
  compiled CUDA in it — pip exits 0 having built nothing. Forced the build by running a real
  `gsplat.rasterization` rather than a bare import: **447.9 s** to compile, producing
  `gsplat_cuda.so` (6.9 MB) in `~/.cache/torch_extensions/py311_cu126/`. The render was real,
  not a silent zero pass: 4898 non-black pixels of 16384, alpha mean 0.12.
- **Two failures on the way, both worth recording.**
  1. First attempt died with "Ninja is required to load C++ extensions". ninja *was* installed;
     the fault was invoking `envs/recon/bin/python` by full path, so the env's `bin` was not on
     `PATH` and torch's `verify_ninja_availability()` could not find it. Run inside an activated
     env.
  2. A later check ran without `TORCH_CUDA_ARCH_LIST` set and torch warned it would compile for
     all visible archs — then did, discarding the cached sm_89 build. **The JIT cache is keyed on
     build config, so the variable is needed at run time, not just install time.** Set it
     permanently in `envs/recon/etc/conda/activate.d/recon_cuda.sh` (plus `~/.bashrc` for
     non-conda shells). Verified: fresh login shell + `conda activate recon` shows
     `TORCH_CUDA_ARCH_LIST=8.9`, and a warm backend load is **6.9 s** against 447 s cold.
- Consequence for later: the kernels live in `~/.cache`, not in the env. Clearing that cache, or
  rebuilding the env, costs 7.5 minutes on the next run. If training ever stalls for minutes
  before iteration 1, this is why.
- Installing nerfstudio downgraded numpy 2.4.6 to 1.26.4. torch and COLMAP re-verified after,
  both unaffected.
