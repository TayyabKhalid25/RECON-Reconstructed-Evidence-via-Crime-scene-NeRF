## Sitting 2 · FTW-38, the lever that was not blocked

FTW-38 says "do not start until phone FPS is measured, because that measurement sets the target".
That holds for the splat *count* budget, and I did not set one. But the ticket assumed count was
the only lever and it is not.

`tools/decimate_splats.py`. Two independent levers:

- `--sh-degree` truncates spherical harmonics. 45 of scene 1's 62 float properties are `f_rest_*`
  SH coefficients — **72.6 % of the file**. Dropping all of them takes the export from
  **44.23 MB to 12.13 MB (3.65x)** and leaves positions, scales, rotations, opacity and base
  colour **bit-identical** (verified by column comparison; bounding box unchanged at
  9.28 x 7.03 x 8.81 m). So `unitScale 0.369573` and every measurement derived from it survive.
  That is what made it safe to do before FTW-30 lands: it cannot move an accuracy figure.
- `--max-splats` ranks by opacity x cross-section and **has no default on purpose**, because the
  budget has to come from a device measurement that does not exist yet.
- `--sh-report` measures the cost rather than assuming it, evaluating real radiance over 400
  random view directions (comparing coefficient magnitudes would be wrong — the basis functions
  have different peak amplitudes per degree). Degree 0 costs mean 3.9/255 sRGB levels, p99 19.2,
  worst case 87. All three columns go in the report, not just the mean; the large excursions are
  specular highlights where view-dependent colour was doing real work.

Finding that contradicts the ticket's own knob order: **an opacity threshold is nearly useless on
our exports.** splatfacto already prunes at `cull-alpha-thresh 0.1`, so only 1.32 % of scene 1's
splats fall below sigmoid opacity 0.1 and 0.02 % below 0.01. Also means gsplat-unity's README
claim that a 0.05 prune drops ~40 % of splats will not reproduce on our data.

Numbers in `docs/RESULTS.md`; the five `tools/` scripts now have an index in `gpu/README.md`,
which they did not before. `npm run typecheck` clean (no web code touched).

**Collider mesh (PR #20, FTW-48).** Section 07's "Poisson mesh export path working, for colliders",

Normals via the SuGaR heuristic: a converged 3D Gaussian lies flat against its surface, so the

which is why it reads the full `.ply` and not just xyz.

Both methods implemented because they fail in opposite directions, measured on scene 1:

| | Poisson d9 | Voxel 0.05 |
|---|---|---|
| Disconnected clusters | **1 091** | **26 705** |
| Bbox coverage per axis | 79 / 71 / 84 % | 58 / 49 / 44 % |
| Median vertex→splat | 0.105 units (≈3.9 cm) | **0.039 units (≈1.4 cm)** |
| p95 | 0.334 units | **0.069 units** |

Poisson is the default and the cluster count is why — a splat cloud is sparse oriented points, so an
occupancy grid shatters and cleaning the fragments deletes half the room. Voxel sits ~3x closer to
the actual splats but leaves holes, and a hole in a collider is a wall shots pass through. Keeping
both is what makes Challenge 1 answerable: same shot into each, divergence should track those
deviation figures.

total triangles. That relative threshold cut the mesh to 8.0 x 4.7 x 7.7 against a
24.7 x 15.5 x 23.5 splat extent — a collider covering a third of the room, physics still running,
shots passing through the rest. A splat surface is legitimately fragmented, so the threshold is now
absolute and per-axis coverage prints every run. The bbox comparison line is what surfaced it, which
is why it stays.

Not claimed: no physical validation (geometry-vs-geometry only), neither mesh watertight, and
nobody has loaded either into Unity as a MeshCollider.

## Sitting 9 · AES-256-GCM at rest

Section 08 milestone (PR #21, FTW-49), chosen because it was the highest-value item left that needs
neither a device nor a database — the crypto is fully testable offline.

Section 08 is explicit that three things get called "encryption at rest" and that we must say which
one we did. This is **option 3, application level envelope encryption**: bytes encrypted before they
reach disk, key in `.env` outside the database, IV and auth tag stored with the ciphertext.

Layout `MAGIC(8) | IV(12) | TAG(16) | ciphertext`, magic `RECONAG1`. **The prefix is load bearing.**
It lets a reader distinguish encrypted from plaintext, so encryption switches on for a deployment
with assets already on disk — no migration, no schema change, no new field in `docs/API.md` — and
switching off still reads the encrypted files. Reversible both ways, the same instinct as the "or a
redirect" seam FTW-13 kept.

Encryption lives inside `writeAsset`, not in the three routes that call it, which keeps the required
ordering right in one place: **hash first, then encrypt**. So the custody SHA-256 stays a hash of
the plaintext the investigator uploaded and `Asset.byteSize` stays the plaintext length — custody
verification is entirely unaffected by whether encryption is on. Added `assetPlaintextSize`, and
`assetByteSize` now documents that it is the on-disk size and must never feed `Content-Length`.

Two loud failures on purpose: a missing or malformed key **throws** rather than silently writing
plaintext, and a bad auth tag raises a typed `EncryptionError` so callers can treat it as a custody
event.

`docs/STACK.md` now carries the statement the report needs — a table of what an attacker with
database access, filesystem access, or both can and cannot read — plus four limitations stated
rather than buried. **The one worth a second opinion: streaming decryption emits plaintext before
GCM's tag is verified**, so a tampered 44 MB `.ply` is partly written to the response before the
stream errors. Streaming anyway, because buffering 44 MB per request to serve a phone over the
tunnel is worse; detection moves to the consumer, which already re-hashes against

## Sitting 10 · Anchoring, closing Decision 1's four `verify` markers

Prompted by committing to ARCore Cloud Anchors over Azure Spatial Anchors. Handbook Section 03
Decision 1 adopted "printed marker plus ARCore Cloud Anchors" with four things marked `verify`, and
**FTW-11 was closed without checking any of them** — its only comment was "ARCore has Cloud Anchor
Option, will explore it further when required". All four now checked against live sources. Written
up in **`docs/ANCHORING.md`**, PR **#22**. Complements Sitting 7, which shipped the endpoints.

The finding that changes the plan: **AR Foundation 6.5, already pinned at 6.5.0 in our manifest,
has a built-in persistent anchor API** (`TrySaveAnchorAsync` / `TryLoadAnchorAsync` /
`TryEraseAnchorAsync`) and the ARCore provider implements it *on top of Cloud Anchors* using our
own GCP project. So `arcore-unity-extensions` may not be needed at all. The catch is real: Unity
documents the returned `SerializableGuid` as platform specific and **not transferable**, and AR
Foundation's separate "shared anchors" feature lists ARCore as **N/A**. Proven for persistence on
one device, undocumented for two. FTW-50 tests both before anything is built on either.

Facts that decide design, all dated 2026-09-02:

- **TTL is 1 to 365 days and over 1 day requires keyless authorization.** An API key caps anchor
  lifetime at 24 hours, shorter than the gap between two lab sessions. Keyless is therefore
  mandatory rather than preferred, which was not previously known and sets FTW-51's scope.
- **Keyless on Android is per signing keystore.** Three developers on three default debug keystores
  means three SHA-1 fingerprints, or `ErrorNotAuthorized` on two phones — which on a phone reads
  as a broken anchor rather than a build configuration problem. One shared custom keystore,
  registered once, release fingerprint at the same time.
- **iOS keyless is a different mechanism entirely** — a backend endpoint minting RS256 JWTs with
  `aud` of `https://arcore.googleapis.com/`. That makes it Track B work, not Unity work, which is
  why FTW-57 is blocked on the Android-only question rather than started.
- **Quotas:** 30 host and 300 resolve requests per minute per IP *and* project, 40 concurrent
  operations per session, unlimited anchors per project. No published price and the docs never ask
  for billing; FTW-51 confirms in console.
- **`arcore-unity-extensions` v1.54.0 shipped 2026-04-22** (from the GitHub API, not the search
  snippet, which said 2025). Declares AR Foundation 6 support since v1.48.0 via the `arf6`
  tarballs, but predates AR Foundation 6.5 and still compiles against deprecated ARF5 symbols.
- **Enable the ARCore API** (`arcore.googleapis.com`). The console still lists "ARCore Cloud Anchor
  API (Legacy)", whose endpoint stopped being supported after 31 Aug 2023.
- **Azure Spatial Anchors was retired 20 November 2024**, announced 1 December 2023. The "why not
  ASA" defence answer is now a checked fact with a date on it.

Design conclusions worth more than the facts:

- **Marker aligns, cloud anchor persists.** Cloud Anchors never give scale, so the printed marker
  stays load bearing even after anchoring works. The 2 cm objective belongs to the *marker* path;
  Google publishes no Cloud Anchor accuracy figure and the error grows with distance from the
  anchor, so anchor drift is measured separately (FTW-56) rather than assumed to meet it.
- **Where anchors are *not* needed, which is most places:** the web viewer, remote 3D viewing, and
  on-site AR while the marker is still on the floor. Cloud Anchors buy persistence after the marker
  is gone, and two devices at once. Nothing else.
- **One anchor per scene, hosted at the marker origin, never one per POI.** POIs are hash-chained
  rows in coordinates we can verify; a cloud anchor id is opaque state on Google's servers we
  cannot verify or re-derive. Anchoring POIs individually turns one re-localisation error into N
  that disagree, and lets a twin partially expire.
- **Hosting uploads scene-derived visual feature data to Google's servers.** Not photographs, but a
  feature map of an investigation site. For a chain-of-custody project that is a stated limitation
  with a mitigation — deliberate TTL, audited host and resolve, purge on case close via the
  Management API `DELETE` (FTW-55) — rather than something to discover at the viva.

## Sitting 11 · Viewer, splat editing, object subsections, offline POI sync

Same prompt, second half, which had been omitted from the original request. Written up in
**`docs/VIEWER-AND-EDITING.md`**, PR **#24**, stacked on `docs/anchoring-decision` so its diff is
only the new work. **Worked in a git worktree** (`.claude/worktrees/docs-viewer-editing`) at
Wahaj's instruction, to stay clear of the other agent — which is the fix for Sitting 10's tangle.

Four findings:

- **"VR" in our own discussion has meant "not in the room",** which is a remote 3D viewer with an
  orbit or first-person camera, not a headset. One is a week on the stack we have; the other needs
  hardware nobody has listed in handbook Section 02. The report must not promise the second while
  shipping the first. FTW-62 exists mostly to force that answer.
- **Do not build a splat editor.** SuperSplat (`playcanvas/supersplat`, **MIT**, TypeScript on the
  PlayCanvas engine, runs in the browser) already has Box and Sphere 3D selection plus
  lasso/polygon/brush/flood in 2D, and a **`Separate`** tool that creates a new splat from a
  selection and removes it from the original — exactly "subsections of splats for each object".
  Use it as an offline tool and ingest its output. A maintained fork of someone else's editor, for
  a feature used a handful of times per case, is a bad trade, and MIT keeps the option open.
- **Learned per-Gaussian segmentation is out on hardware grounds, not preference.** SAGA's paper
  reports all training and inference on a single **24 GB RTX 3090**; a published comparison puts
  **Gaussian Grouping at ~61 GB peak VRAM**. We have 8 GB and 6 GB and are already fighting VRAM on
  plain splatfacto, and each method means retraining every scene through a modified pipeline. Goes
  in the report as a scoped-out alternative with its reason, which reads better than silence.
- **Offline POI editing and the hash chain coexist only if the client never computes a chain
  hash.** The chain is append-only and server-ordered; a phone with no network cannot know what the
  previous row will be. Design: the client keeps a journal of *intents* with client-generated UUIDs
  as the POI ids; the server replays them in receipt order, stamps its own clock, and computes
  `prevHash`/`rowHash` itself. Client time is kept as a *claimed* field, never as the custody time.
  Letting clients chain would produce a tamper-evidence claim that does not hold, which is strictly
  worse than having no chain. Conflicts by version integer and 409, not CRDTs. Deletes are
  tombstones. Drafts are visibly draft and cannot be exported.

Also separated **three things that all get called "editing"** and must not share a code path:
cleanup (crops floaters — *modifies evidence*, must be pre-ingest, logged, original retained,
FTW-66), segmentation (additive, original `sha256` stays valid), and annotation (database rows,
must be *incapable* of touching splat data, enforced by a test). That last one is the answer to
"how do you know the investigator didn't move the body", and it is free to design in now.

Formats: PLY stays authoritative because `metadata.json`'s `sha256` covers it and every accuracy
figure derives from it. SOG (~15-20x smaller) or SPZ (~10x) ship *alongside* for web delivery, both
lossy, and the viewer states which asset is on screen so nobody measures a quantised scene.
Composes with Sitting 2's SH truncation (3.65x, bit-identical geometry) rather than competing.

Recommendation going into FTW-59: **Spark** (`sparkjsdev/spark`, three.js + WebGL2) for the
dashboard viewer — the only candidate whose documented features already include several splat
objects in one scene *and* a VR path, on the stack we are committed to. Measured, not assumed.
