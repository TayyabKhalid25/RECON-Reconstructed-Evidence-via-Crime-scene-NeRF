## Sitting 2 · FTW-38, the lever that was not blocked

FTW-38 says "do not start until phone FPS is measured, because that measurement sets the target".
That holds for the splat *count* budget, and I did not set one. But the ticket assumed count was
the only lever and it is not.

`tools/decimate_splats.py`. Two independent levers:

- `--sh-degree` truncates spherical harmonics. 45 of scene 1's 62 float properties are `f_rest_*`
  SH coefficients — **72.6 % of the file**. Dropping all of them takes the export from
  **44.23 MB to 12.13 MB (3.65x)** and leaves positions, scales, rotations, opacity and base
  colour **bit-identical** (verified by column comparison; bounding box unchanged at
  9.28 x 7.03 x 8.81 m). So `unitScale 0.369573` and every measurement derived from it survive.
  That is what made it safe to do before FTW-30 lands: it cannot move an accuracy figure.
- `--max-splats` ranks by opacity x cross-section and **has no default on purpose**, because the
  budget has to come from a device measurement that does not exist yet.
- `--sh-report` measures the cost rather than assuming it, evaluating real radiance over 400
  random view directions (comparing coefficient magnitudes would be wrong — the basis functions
  have different peak amplitudes per degree). Degree 0 costs mean 3.9/255 sRGB levels, p99 19.2,
  worst case 87. All three columns go in the report, not just the mean; the large excursions are
  specular highlights where view-dependent colour was doing real work.

Finding that contradicts the ticket's own knob order: **an opacity threshold is nearly useless on
our exports.** splatfacto already prunes at `cull-alpha-thresh 0.1`, so only 1.32 % of scene 1's
splats fall below sigmoid opacity 0.1 and 0.02 % below 0.01. Also means gsplat-unity's README
claim that a 0.05 prune drops ~40 % of splats will not reproduce on our data.

Numbers in `docs/RESULTS.md`; the five `tools/` scripts now have an index in `gpu/README.md`,
which they did not before. `npm run typecheck` clean (no web code touched).

**Collider mesh (PR #20, FTW-48).** Section 07's "Poisson mesh export path working, for colliders",

Normals via the SuGaR heuristic: a converged 3D Gaussian lies flat against its surface, so the

which is why it reads the full `.ply` and not just xyz.

Both methods implemented because they fail in opposite directions, measured on scene 1:

| | Poisson d9 | Voxel 0.05 |
|---|---|---|
| Disconnected clusters | **1 091** | **26 705** |
| Bbox coverage per axis | 79 / 71 / 84 % | 58 / 49 / 44 % |
| Median vertex→splat | 0.105 units (≈3.9 cm) | **0.039 units (≈1.4 cm)** |
| p95 | 0.334 units | **0.069 units** |

Poisson is the default and the cluster count is why — a splat cloud is sparse oriented points, so an
occupancy grid shatters and cleaning the fragments deletes half the room. Voxel sits ~3x closer to
the actual splats but leaves holes, and a hole in a collider is a wall shots pass through. Keeping
both is what makes Challenge 1 answerable: same shot into each, divergence should track those
deviation figures.

total triangles. That relative threshold cut the mesh to 8.0 x 4.7 x 7.7 against a
24.7 x 15.5 x 23.5 splat extent — a collider covering a third of the room, physics still running,
shots passing through the rest. A splat surface is legitimately fragmented, so the threshold is now
absolute and per-axis coverage prints every run. The bbox comparison line is what surfaced it, which
is why it stays.

Not claimed: no physical validation (geometry-vs-geometry only), neither mesh watertight, and
nobody has loaded either into Unity as a MeshCollider.

## Sitting 9 · AES-256-GCM at rest

Section 08 milestone (PR #21, FTW-49), chosen because it was the highest-value item left that needs
neither a device nor a database — the crypto is fully testable offline.

Section 08 is explicit that three things get called "encryption at rest" and that we must say which
one we did. This is **option 3, application level envelope encryption**: bytes encrypted before they
reach disk, key in `.env` outside the database, IV and auth tag stored with the ciphertext.

Layout `MAGIC(8) | IV(12) | TAG(16) | ciphertext`, magic `RECONAG1`. **The prefix is load bearing.**
It lets a reader distinguish encrypted from plaintext, so encryption switches on for a deployment
with assets already on disk — no migration, no schema change, no new field in `docs/API.md` — and
switching off still reads the encrypted files. Reversible both ways, the same instinct as the "or a
redirect" seam FTW-13 kept.

Encryption lives inside `writeAsset`, not in the three routes that call it, which keeps the required
ordering right in one place: **hash first, then encrypt**. So the custody SHA-256 stays a hash of
the plaintext the investigator uploaded and `Asset.byteSize` stays the plaintext length — custody
verification is entirely unaffected by whether encryption is on. Added `assetPlaintextSize`, and
`assetByteSize` now documents that it is the on-disk size and must never feed `Content-Length`.

Two loud failures on purpose: a missing or malformed key **throws** rather than silently writing
plaintext, and a bad auth tag raises a typed `EncryptionError` so callers can treat it as a custody
event.

`docs/STACK.md` now carries the statement the report needs — a table of what an attacker with
database access, filesystem access, or both can and cannot read — plus four limitations stated
rather than buried. **The one worth a second opinion: streaming decryption emits plaintext before
GCM's tag is verified**, so a tampered 44 MB `.ply` is partly written to the response before the
stream errors. Streaming anyway, because buffering 44 MB per request to serve a phone over the
tunnel is worse; detection moves to the consumer, which already re-hashes against
`X-Asset-SHA256`. Also recorded plainly: **sensitive-column encryption (option 2) is not done**, so
the claim is scoped to assets.

36 checks in `scripts/check-encryption.ts`, in `npm run verify`, no database. Tampering is tested
per region separately (ciphertext first and last byte, IV, tag, magic, truncation), 200 encryptions
of identical plaintext give 200 distinct IVs, and there is a real storage-layer round trip on actual
files including the safe-rollout case and a tampered file erroring mid-stream rather than being
