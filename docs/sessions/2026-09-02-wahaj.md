The substance of the PR is real and valuable: it identifies the actual Track C blocker.
Both `aras-p/UnityGaussianSplatting` and the `wuyize25/gsplat-unity` fork use HLSL wave
intrinsics (`wavebasic`, `waveballot`) in the `SplatUtilities.compute` radix sort. Mobile
GPUs (Mali, Adreno) do not support these, and the failure takes down the whole shader file,
not just the sort kernel. That is exactly the Section 05 risk the handbook told us to find
in week 1, and it was found in week 1.

Verified independently from the branch rather than from the PR description:

  claim is not in the diff.
- **Dangling `GsplatURPFeature`** left in `URP-Performant-Renderer.asset` with `m_Active: 0`.
  If the package really does get removed later, that is a missing-script reference in the
  renderer asset.
- **`.bytes` are untracked going forward but still in history** (commit `822ba6f`).
  `git rm --cached` does not shrink the clone. Per AGENTS.md the fix for "large binary landed
  in git" is not deleting the pointer.
- **`ChristmasTree.asset` / `luigi.asset` are now broken on a fresh clone.** They are
  `GaussianSplatAsset` files whose `m_PosData`/`m_SHData`/etc. point at the five `.bytes`

- **New `Unity/Recon/.gitattributes` adds LFS filters** for `png/ttf/dll/so/zip/fbx/...`.
  These are the LFS rules that were previously (wrongly) inside `.gitignore`, so moving them
  is correct in itself, but it sets up Git LFS on a repo whose rule is that large binaries do
  not enter git at all. We have no LFS budget on a free private plan. Wants a decision, not a
  silent adoption.
- **`AndroidMinSdkVersion` dropped 34 → 29** and Android graphics APIs became
  `15 00 00 00, 0b 00 00 00` (Vulkan first, then GLES3). Both are consequential for a mobile
  compute-shader path and are unexplained in the PR body. GLES3.1 vs Vulkan is precisely the
  axis on which splat compute support differs.

## Sitting 2 · FTW-38, the lever that was not blocked

FTW-38 says "do not start until phone FPS is measured, because that measurement sets the target".
That holds for the splat *count* budget, and I did not set one. But the ticket assumed count was
the only lever and it is not.

`tools/decimate_splats.py`. Two independent levers:

- `--sh-degree` truncates spherical harmonics. 45 of scene 1's 62 float properties are `f_rest_*`
  SH coefficients — **72.6 % of the file**. Dropping all of them takes the export from
  **44.23 MB to 12.13 MB (3.65x)** and leaves positions, scales, rotations, opacity and base
  colour **bit-identical** (verified by column comparison; bounding box unchanged at
  9.28 x 7.03 x 8.81 m). So `unitScale 0.369573` and every measurement derived from it survive.
  That is what made it safe to do before FTW-30 lands: it cannot move an accuracy figure.
- `--max-splats` ranks by opacity x cross-section and **has no default on purpose**, because the
  budget has to come from a device measurement that does not exist yet.
- `--sh-report` measures the cost rather than assuming it, evaluating real radiance over 400
  random view directions (comparing coefficient magnitudes would be wrong — the basis functions
  have different peak amplitudes per degree). Degree 0 costs mean 3.9/255 sRGB levels, p99 19.2,
  worst case 87. All three columns go in the report, not just the mean; the large excursions are
  specular highlights where view-dependent colour was doing real work.

Finding that contradicts the ticket's own knob order: **an opacity threshold is nearly useless on
our exports.** splatfacto already prunes at `cull-alpha-thresh 0.1`, so only 1.32 % of scene 1's
splats fall below sigmoid opacity 0.1 and 0.02 % below 0.01. Also means gsplat-unity's README
claim that a 0.05 prune drops ~40 % of splats will not reproduce on our data.

Numbers in `docs/RESULTS.md`; the five `tools/` scripts now have an index in `gpu/README.md`,
which they did not before. `npm run typecheck` clean (no web code touched).

## Sitting 3 · Whether to deviate on the renderer

Researched the mobile splat landscape and verified every load-bearing claim against the actual
repos rather than search results. Written up in **`docs/MOBILE-SPLAT-OPTIONS.md`**.

The headline: **Tayyab's diagnosis is right, but the conclusion "start fresh and write a bitonic
sort" is probably wrong, and the package PR #14 removes is the one documented to work on Android.**

- Audited pragma placement across every `.compute` in both repos. aras-p declares
  `require wavebasic/waveballot/use_dxc` in `SplatUtilities.compute` — **the same file as all 19
  kernels**, 15 of which are non-sorting (`CSCalcViewData`, `CSCalcDistances`, ...). Pragmas are
  file-scoped, so rendering dies, not just sorting. That fully explains "no splats at all".
- `gsplat-unity` **quarantines those pragmas in `Gsplat.compute` (5 sort kernels)**; its other six
  compute files have zero wave pragmas. Its README says it was tested on **Android**. So the
  structural fix FTW-44 proposes to write by hand already exists upstream.
- `arloopa/UnitySplats` (MIT, Unity 6000.0+, URP) advertises an **OpenGL ES 3.1 async-CPU-sort
  path tested on Samsung and HONOR**, and `Runtime/GsplatSorter.cs:451` really does catch a
  wave-op compile failure and fall back to CPU instead of dying. New though — 32 stars, first
  release last month — so it wants an audit and a pinned hash, not blind trust.
- Against the bitonic plan specifically: no success report anywhere, Unity's tracker documents
  bitonic exceeding max workgroup size on Adreno/Mali, aras-p #112 has been open since 2024 and
  was still being fought in Jan 2026, and the Vulkan wave-size bug it partly targets is already
  patched upstream in `SortCommon.hlsl`. If FTW-44 proceeds, the cheap version is **splitting
  `SplatUtilities.compute`**, not rewriting the sort.
- Costed handbook Option 3 (mesh on mobile) properly, since it is the only option that touches my
  tracks: `AssetKind` has exactly three values and the asset route hardcodes
  `kind: 'SPLAT_PLY'`, so two deliverables per scene is a real `docs/API.md` change needing all
  three of us. Web side is half a day thanks to the "or a redirect" seam FTW-13 kept; the actual
  work is GPU-side meshing, and PlayCanvas-style marching cubes outputs **geometry only, no
  colour**, so "textured mesh" needs a separate bake step. We should build the mesh anyway for
  ballistics colliders.
- Ruled out WebView/PlayCanvas as the AR path: a WebView cannot receive the ARCore pose, so
  marker alignment is lost. Good for the dashboard viewer, which Track B wants regardless.
